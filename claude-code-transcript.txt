  2. Database Schema

  -- Applied per connection
  PRAGMA journal_mode = WAL;          -- persistent, set once at init
  PRAGMA synchronous = NORMAL;        -- safe with WAL, much faster commits
  PRAGMA busy_timeout = 5000;         -- wait for the writer lock instead of 
  SQLITE_BUSY
  PRAGMA foreign_keys = ON;

  CREATE TABLE IF NOT EXISTS reservations (
      supplier_id      TEXT    NOT NULL,
      reservation_id   TEXT    NOT NULL,
      payload_hash     BLOB    NOT NULL,          -- SHA-256, 32 bytes
      payload_json     TEXT    NOT NULL,          -- latest accepted canonical 
  payload
      updated_at_utc   TEXT    NOT NULL,          -- ISO-8601 UTC, from the 
  supplier (version clock)
      first_seen_utc   TEXT    NOT NULL,
      last_modified_utc TEXT   NOT NULL,          -- server time of last real 
  change
      version          INTEGER NOT NULL DEFAULT 1,
      PRIMARY KEY (supplier_id, reservation_id)
  ) WITHOUT ROWID;

  CREATE TABLE IF NOT EXISTS supplier_stats (
      supplier_id        TEXT PRIMARY KEY,
      total_received     INTEGER NOT NULL DEFAULT 0,
      created_count      INTEGER NOT NULL DEFAULT 0,
      updated_count      INTEGER NOT NULL DEFAULT 0,
      duplicate_count    INTEGER NOT NULL DEFAULT 0,
      stale_count        INTEGER NOT NULL DEFAULT 0,
      throttled_count    INTEGER NOT NULL DEFAULT 0,
      last_request_utc   TEXT
  ) WITHOUT ROWID;

  Indexing:
  - The composite PK is the lookup index. Lookup by (supplier_id, 
    reservation_id) is a single B-tree seek, and WITHOUT ROWID stores the row in
    that tree, which avoids a second lookup.
  - No other indexes for the core flow, because extra indexes slow writes.
  - If the brief wants "list reservations by supplier", the PK prefix already
    covers it. A secondary index on (supplier_id, updated_at_utc) would only be
    added if a query needs it.

  Stats updates: counters are updated with INSERT ... ON CONFLICT(supplier_id) 
  DO UPDATE SET x = x + 1 in the same transaction as the reservation write. For
  throttled requests there's no reservation write, so it's a tiny standalone
  upsert.

  3. Concurrency & Rate Limiting

  Algorithm: a sliding-window log, which gives a strict rolling window.
  Fixed-window and token-bucket approaches allow bursts of up to 2× at
  boundaries, so I'm not using them.

  - ConcurrentDictionary<string, SupplierWindow> holds one window per supplier.
  - Each SupplierWindow holds a Queue<long> of admission timestamps (monotonic
    ticks from TimeProvider.GetTimestamp()) and a private lock object.
  - TryAcquire(supplierId) runs under that supplier's lock:
    a. Dequeue every timestamp ≤ now − 60s.
    b. If queue.Count >= 100, reject and return retryAfter = oldest + 60s − now.
    c. Otherwise enqueue now and admit.
  - The check and the enqueue are one critical section, so parallel bursts can't
    oversubscribe the limit. The lock is per supplier, so suppliers don't block
    each other. Critical section cost is O(evicted), amortized O(1).
  - Memory is bounded at 100 timestamps per supplier. Idle supplier windows are
    pruned lazily.

  Ordering within a request: validate first (cheap, doesn't consume quota), then
  throttle, then dedup/persist. Throttled requests return 429 with a
  Retry-After header and a ProblemDetails body.

  What counts toward the limit: every admitted request counts, including ones
  that turn out to be duplicates or stale. Duplicates are exactly what a
  misbehaving feed floods us with, so they should be throttled too. Rejected
  429s don't consume quota.

  DB-level safety under parallelism:
  - Each ingest runs in BEGIN IMMEDIATE. SQLite then serializes writers up
    front, so the read-compare-write sequence for a reservation can't interleave
    and there's no deferred-lock upgrade deadlock. Readers are unaffected under
    WAL.
  - Short transactions plus busy_timeout handle queueing. Under parallel bursts
    to the same reservationId, writers queue and each sees the previous result.
  - One connection per request, from a factory that applies the PRAGMAs.

  Trade-off: the limiter is in-memory, so it assumes a single instance and
  resets on restart. That is acceptable for this brief, and the README will say
  so. A persisted rate_events table would give restart-safety at the cost of a
  write per request.

  4. Dedup & Idempotency Logic

  Key: (supplierId, reservationId).

  Payload hash:
  - Canonicalize the business fields: fixed field order, trimmed strings,
    invariant-culture decimals, UTC-normalized dates, and updatedAtUtc excluded.
  - Serialize that and take SHA-256, stored as a 32-byte BLOB.
  - Compare with SELECT payload_hash, updated_at_utc FROM reservations WHERE 
    supplier_id=@s AND reservation_id=@r, which reads two small columns and
    never the full payload.

  Decision flow inside the BEGIN IMMEDIATE transaction:

  ┌───────────┬──────────────────────┬─────────────────────┬───────────────┐
  │   Case    │      Condition       │       Action        │  Outcome /    │
  │           │                      │                     │     HTTP      │
  ├───────────┼──────────────────────┼─────────────────────┼───────────────┤
  │ New       │ no row               │ INSERT, version=1   │ Created / 201 │
  ├───────────┼──────────────────────┼─────────────────────┼───────────────┤
  │ Identical │ hash equal           │ no write to         │ Duplicate /   │
  │           │                      │ reservations        │ 200           │
  ├───────────┼──────────────────────┼─────────────────────┼───────────────┤
  │           │ hash differs and     │                     │               │
  │ Stale     │ incoming             │ no write            │ StaleIgnored  │
  │           │ updatedAtUtc <       │                     │ / 200         │
  │           │ stored               │                     │               │
  ├───────────┼──────────────────────┼─────────────────────┼───────────────┤
  │           │ hash differs and     │ UPDATE payload,     │               │
  │ Update    │ incoming             │ hash, timestamp,    │ Updated / 200 │
  │           │ updatedAtUtc >       │ version+1           │               │
  │           │ stored               │                     │               │
  ├───────────┼──────────────────────┼─────────────────────┼───────────────┤
  │ Conflict  │ hash differs and     │ no write            │ Conflict /    │
  │           │ updatedAtUtc equal   │                     │ 409           │
  └───────────┴──────────────────────┴─────────────────────┴───────────────┘

  - Identical payloads: the hash comparison runs first. Identical bytes are a
    no-op regardless of timestamp, which makes retries safe and idempotent.
  - Changed details on an existing id: accepted only if the incoming timestamp
    is strictly newer, so the stored row never moves backwards.
  - Out-of-order / stale: an older updatedAtUtc with different content is
    ignored. The response includes the stored timestamp so the supplier can see
    why. A stale arrival with identical content is classed as Duplicate.
  - Equal timestamp, different content: this is ambiguous, so I reject it with
    409 rather than silently choose a winner. I'd flag this in the README.
  - Stats: the relevant counter is incremented in the same transaction.
  - Validation: supplierId and reservationId are required and length-capped,
    updatedAtUtc must be a valid UTC timestamp, and bad input returns 400.

  Endpoints:
  - POST /api/suppliers/{supplierId}/reservations
  - GET /api/suppliers/{supplierId}/reservations/{reservationId}
  - GET /api/suppliers/{supplierId}/stats
  - GET /health

  5. Testing Strategy (xUnit integration)

  Infrastructure: WebApplicationFactory<Program> with a unique temp SQLite file
  per test class, replacing TimeProvider with FakeTimeProvider. Real SQLite and
  real HTTP, with no repository mocks.

  Scenarios:
  - Basic ingest: a new reservation returns 201 and is retrievable. Invalid
    payloads return 400.
  - Identical resend: returns Duplicate, the row's version and last_modified_utc
    are unchanged, and the duplicate counter increments.
  - Changed details with newer updatedAtUtc: returns Updated, and the version
    increments.
  - Stale update (older updatedAtUtc, different content): returns StaleIgnored
    and the stored data is unchanged.
  - Out-of-order sequence: deliver v3, then v1, then v2, and the final state is
    v3.
  - Equal timestamp, different content: returns 409.
  - Same reservationId under different suppliers: the records are independent.
  - Rate limit boundary: requests 1–100 succeed, the 101st returns 429 with
    Retry-After, and throttled requests don't consume quota.
  - Rolling window: advance the fake clock by 59.9s and the request is still
    blocked. Advance past 60s and exactly the aged-out slots free up (not a full
    reset, which proves it is rolling and not fixed-window).
  - Per-supplier isolation: throttling supplier A doesn't affect supplier B.
  - Parallel burst: 300 concurrent requests for one supplier give exactly 100
    accepted and 200 throttled.
  - Concurrent same-reservation writes: N parallel requests for one
    reservationId with the same payload give exactly one Created, the rest
    Duplicate, and one row. A variant with different timestamps ends on the
    highest timestamp.
  - Stats endpoint: counters match the observed outcomes.
  - Persistence: WAL mode is active (PRAGMA journal_mode returns wal).

  6. Postman Collection

  SupplierFeed.postman_collection.json plus an environment with baseUrl and
  supplierId. Each request has test scripts that assert status and outcome.

  Supplier Feed Throttle & Dedup
  ├─ 0. Health
  ├─ 1. Ingest

  │   └─ Invalid payload                     (400)

  │   ├─ Get reservation

  + Retry-After

  Pre-request scripts generate unique reservationIds and ISO timestamps. The
  Rate Limiting folder is meant for the Collection Runner with about 105

  Assumptions and open questions

  1. Does a duplicate or stale request consume rate-limit quota? I assumed yes,
     for the reason in section 3.
  2. What status for a stale update? I proposed 200 with an outcome field, which

     brief say?
  3. Is updatedAtUtc excluded from the payload hash? I assumed yes. If the brief
     treats a timestamp-only change as an update, it should be included.
  4. Is a single instance acceptable? The limiter is in-memory.
  5. Is supplierId in the URL or the body? I assumed the URL.
  6. What are the payload fields? I'll define a minimal set of business fields
     (guest name, dates, status, amount, currency) unless the brief specifies
     them.

  What I built
  - PayloadHasher: hashes roomId (trimmed), checkIn and checkOut (ISO-8601 UTC)
    and price ("0.00", invariant culture) with SHA-256. 450 and 450.00 hash the
    same.
  - ReservationRepository: has GetByCompositeKeyAsync (full row),
    GetFingerprintByCompositeKeyAsync (hash and updated_at_utc only, which the
    service uses), InsertAsync and UpdateAsync. UpdateAsync has AND 
    updated_at_utc < @UpdatedAtUtc in its WHERE clause and returns whether a row
    changed.
  - SupplierStatsRepository: one INSERT ... ON CONFLICT DO UPDATE records any
    outcome, and an unknown supplier reads back as zeros.
  - SlidingWindowRateLimiter: keeps a per-supplier queue of timestamps behind a
    lock, in a ConcurrentDictionary, using TimeProvider. It allows 100 requests
    per rolling 60s, configurable under RateLimit. A request is blocked until
    the oldest one is a full 60s old.
  - ReservationIngestService: runs validation, then the throttle check, then the
    dedup and write. The dedup and write run inside BEGIN IMMEDIATE (a small
    ImmediateTransaction helper), so parallel writes to one reservation queue
    instead of racing.
  - ReservationsController:
    - POST /api/reservations/ingest returns 201 for a new reservation, 200 for
      Duplicate, Updated and StaleIgnored, 400 for invalid input, and 409 for
      the equal-timestamp conflict. It returns 429 with Retry-After when
      throttled.
    - GET /api/reservations/stats/{supplierId} returns { supplierId, 
      ingestedCount, throttledCount }, with zeros for an unknown supplier.

  Smoke-test results (limit 5): requests 1–5 gave Created, Duplicate, Updated,
  StaleIgnored and Conflict (409). An invalid price returned 400 and didn't use
  up quota. The 6th request returned 429 with Retry-After: 60. Stats then showed
  ingested 5, throttled 1, and an unknown supplier showed 0 and 0.

  Differences from your spec
  1. Throttled counting: the service records a throttled request in the stats
     table when the limiter rejects it, not the limiter itself. This keeps the

     DOTNET_ROLL_FORWARD=LatestMajor. I used that for the smoke test.
  3. Price rounding: a price like 450.004 and 450.00 hash identically, because
